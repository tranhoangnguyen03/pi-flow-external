# Design: named Pi harness configurations (`pi-*`)

Status: design ready for review. No code changes made by this document. Supersedes the earlier draft at `~/.claude/plans/parent-conversation-snapshot-recent-zippy-kazoo.md`, which is read-only input to this doc and is not part of this repository.

## 1. What this adds

Today `Agent`/`workflow` delegate to exactly three external CLI harnesses: `agy`, `claude`, `codex`, selected by `role` + optional `harness`. This design adds a fourth delegation surface: **named Pi harness configurations** — arbitrary `pi-<label>` names (e.g. `pi-deepseek`, `pi-glm`, `pi-fast`) that each pin a `provider/model` id (any model resolvable through Pi's own `ModelRegistry` — self-hosted, OpenAI-compatible, or any other registered provider, not "local-only") and an optional thinking level. A named pi config is called exactly like any other harness:

```
Agent({ role: "reviewer", harness: "pi-deepseek", prompt: "..." })
```

The six roles already shipped by this extension (`explorer`, `planner`, `implementer`, `reviewer`, `qa`, `worker`) become automatically available on every registered `pi-*` config the moment it is registered — no per-config file authoring, no per-role opt-in list. `agy`, `claude`, and `codex` — their profiles, resolution, permission mapping, and CLI execution — are **completely unchanged** by this feature.

This activates a runtime path that already exists but is currently dead: `src/core/spawn.ts`'s in-process `createAgentSession` branch (lines 449–619), reachable today only by `backend: "pi"`, which is unconditionally rejected before it can run (`src/profiles.ts:174-180` excludes it from the catalog; `src/pi-subagent.ts:382-391` hard-rejects it a second time). This design narrows that rejection to a precise legitimacy rule instead of removing it, and finishes the dormant runtime so it is trustworthy to actually run.

## 2. Corrections this design makes to the earlier draft

The earlier draft (read as input; not adopted verbatim) proposed three things this design explicitly rejects, per direct instruction:

1. **No arbitrary `claude → codex → agy` donor-fallback chain** for role bodies. Instead, every shared role body comes from **one canonical source**: the `DEFAULT_ROLES` data already in `src/defaults.ts` (extracted to a shared leaf module — see §4). This is not a new concept; it is the *same* data that already generates the `claude-*`/`codex-*`/`agy-*` files today (`src/defaults.ts:13-44`, `buildDefaultProfile()`). A `pi-*` config simply becomes a fourth consumer of that one source, not a reader of whichever external-CLI file happens to exist or be customized.
2. **No second "plural harnesses" profile format.** The draft's `role:` + `harnesses: [...]` shared-file shape is dropped entirely. There is exactly one mechanism for shared role bodies (canonical synthesis, §4), plus the pre-existing, unchanged single-backend markdown format for anyone who writes a real file.
3. **No mechanically-false "readonly" claim.** The draft's tier→tool-exclusion table (excluding `bash`/`edit`/`write` by name) was correct as far as it went, but incomplete: it said nothing about the fact that, as currently coded, a child session loads the **entire local extension surface** (every project/user-installed pi extension), so a "readonly" tier only ever excluded 4 names while arbitrary third-party tools remained reachable. §6 resolves this honestly: child sessions load **no extensions, skills, prompt templates, or themes** (`noExtensions: true` and siblings), so the tier table's 4 built-in names are the *entire* tool surface a tier can act on — the claim becomes mechanically true instead of superficially true.

## 3. Domain vocabulary additions (for `AGENTS.md`/`CONTEXT.md` at implementation time)

- **Named Pi harness configuration ("pi harness"):** an entry in `harnesses.json`, keyed by a `pi-`-prefixed label, pinning a `provider/model` id and optional thinking level for in-process execution via Pi's own SDK. Not a CLI; runs in the same process as the parent.
- **Canonical role synthesis:** producing an in-memory `SubagentProfile` for `<pi-harness>-<role>` from the shared `DEFAULT_ROLES` definition, applied identically to every registered pi harness, the same way `agy-*`/`claude-*`/`codex-*` files are already generated from that same definition.
- **Harness identity vs. execution backend:** `backend` (`"pi" | "codex" | "claude" | "agy"`) selects *how* a profile runs; the new `harness` field selects *which configuration* — for `agy`/`claude`/`codex` these are always equal (harness defaults to backend), but for a pi profile `backend` is always the literal `"pi"` while `harness` is the specific `pi-*` label.

## 4. Schema and canonical role reuse

### 4.1 `SubagentProfile.harness?: string` (`src/types.ts`)

Add one optional field. Every existing `SubagentProfile` consumer that reads `profile.backend` to mean *selector identity* switches to `profile.harness ?? profile.backend`; every consumer that reads it to mean *execution mechanism* is untouched. Concretely:

- Selector-identity consumers to change: `externalProfileRole()`, `externalRoleAvailability()`'s grouping key, the `${harness}-${role}` lookup in `resolveExternalProfile()`.
- Execution-mechanism consumers, unchanged: `resolvePermission()`, `usesPiBackend()`/`resolveProfileModel()`, `spawnSubagentRuntime()`'s dispatch `if` chain.

Zero changes required to any existing `agy-*.md`/`claude-*.md`/`codex-*.md` file: `harness` is absent, defaults to `backend`, identical behavior. This is the same reasoning the earlier draft used and it still holds; nothing here changed.

### 4.2 Harness registry: `~/.pi/agent/pi-flow-external/harnesses.json`

Sibling to `settings.json`, same directory, same posture (global, not project-scoped, never trust-gated — matching `settings.json`, not the project-only `defaultHarness` override).

```json
{
  "version": 1,
  "harnesses": {
    "pi-deepseek": { "model": "deepseek/deepseek-chat", "thinking": "high", "owner": "user" },
    "pi-glm": { "model": "zhipu/glm-4.6" }
  }
}
```

- **Key format:** `/^pi-[a-z0-9][a-z0-9-]*$/`. Enforced at both creation time and load time. This permanently forecloses collision with `agy`/`claude`/`codex` and with any future built-in harness name (all reserved names are non-`pi-`-prefixed).
- **`model` (required):** `provider/modelId`, same string format as `SubagentProfile.model`, resolved via `ctx.modelRegistry.find(provider, modelId)` — confirmed synchronous, no network call (`node_modules/@earendil-works/pi-coding-agent/dist/core/model-registry.d.ts:60`). Any model the user's Pi installation can already resolve is eligible — a self-hosted/OpenAI-compatible/custom-registered provider works exactly the same as a built-in one, satisfying "any available Pi model, not local-only."
- **`thinking` (optional at the interview prompt; always persisted explicitly):** must be one of the SDK's own closed thinking-level literals — `"off" | "minimal" | "low" | "medium" | "high" | "xhigh"` (`@earendil-works/pi-agent-core`'s `ThinkingLevel` type; confirmed at `node_modules/@earendil-works/pi-agent-core/dist/types.d.ts:249` — the same type `createAgentSession({ thinkingLevel })` and `AgentSession.getAvailableThinkingLevels()` consume). This is a deliberate departure from this repo's existing loose `ThinkingLevel = string` alias (`src/types.ts:8`, used by `claude-*`/`codex-*`/`agy-*` profiles): a named pi harness pins its thinking level from the SDK's own real vocabulary, not a free string, because that value is fed directly into the pinned SDK's session constructor rather than into an external CLI's own argv/flag parsing. If the creation interview doesn't collect a value, the entry is written with `thinking: "off"` **explicitly persisted** — never left absent to silently inherit `createAgentSession`'s own "else 'medium'" default at session-creation time (confirmed default in `dist/core/sdk.js:121-123`). Validated against this closed six-value set both at creation (reject an unsupported or misspelled value immediately, before writing `harnesses.json`, with the live valid list in the error) and at load time in `loadHarnessConfigs` (an entry whose `thinking` is outside the six literals is dropped with a diagnostic, same posture as a bad `model` string). **Implementation-time check:** the pinned devDependency (`0.79.4`) exposes this list only as a TypeScript type, not a runtime-exported constant array; confirm at implementation time whether the newer host CLI (`0.85.1`, referenced in §7) still uses the same six values before hand-maintaining this literal list, and prefer a runtime-queryable source (e.g. a future SDK export) over a duplicated array if one becomes available.
- **`owner` (optional):** same tagging convention as `SubagentProfile.owner` — a user-authorship marker stamped for consistency and future-proofing.
- **Invalid-entry behavior:** migrate-on-read, never-fatal, exactly the idiom already used by `src/settings.ts:63-113` and `src/profiles.ts`'s per-file `parseProfileFile` (`return undefined` on failure). An entry missing `model`, with an unparseable `model` string, or a key not matching the `pi-` pattern is **dropped from the live map with a diagnostic string**; the rest of the file loads normally. Unknown top-level keys are diagnostics, not fatal, same as `settings.ts`.
- **New module `src/harnesses.ts`:** `loadHarnessConfigs(agentDir): { harnesses: Map<string, HarnessConfig>; diagnostics: string[] }`, `getConfiguredHarnessNames(agentDir): Set<string>` (pi-registry keys only — the three external harnesses are already available via `EXTERNAL_HARNESSES` and are not duplicated here).
- **Atomic writes & concurrency:** creation goes through the **same smoke-test/staging/rollback machinery already built for markdown profiles** (`installProfileWithSmokeTest`, `src/profile-creator.ts`), retargeted to write JSON instead of a `subagents/*.md` file: stage a temp file in `pi-flow-external/`, run a real smoke test (see §7.3 — this literally exercises the pi runtime this design completes, which is a good property: a broken pi runtime fails harness creation immediately instead of silently), then atomically commit via same-directory file rename, or roll back on any failure. No silent overwrite of an existing key — same "already exists" rejection posture as profile files. **Concurrency note:** same-directory rename guarantees filesystem integrity (readers never observe a missing, truncated, or half-written `harnesses.json`), but because there is no inter-process registry lock, concurrent distinct-name writers follow last-writer-wins and can lose an update if racing; it is an atomic file replace, not an ACID multi-process database transaction.

### 4.3 Legitimacy rule (anti-spoofing) — unchanged from the earlier draft, still correct

A `backend: "pi"` profile is external-delegation-eligible only when **both**: (1) its frontmatter declares `harness: <name>`, and (2) `<name>` exists in the live `harnesses.json` registry with a resolvable `model`. Concretely:

```
isExternalAgentProfile(profile, configuredPiHarnesses) =
  EXTERNAL_HARNESSES.includes(profile.backend)
  || (profile.backend === "pi" && profile.harness !== undefined && configuredPiHarnesses.has(profile.harness))
```

This is the exact mechanical reason an ordinary native-Pi-subagent file (no `harness:` field, or one naming an unregistered config) can never accidentally qualify — condition (2) requires a name that only this extension's own harness registry can supply. `isExternalAgentProfile`/`filterExternalAgentProfiles` (`src/profiles.ts:174-180`) take the live configured-harness-name set as a parameter; every call site threads it through (see §9 for the full ripple list). The existing negative-control test fixtures (`local-reviewer` with bare `backend: pi`, native `explorer`/`general-purpose`) satisfy neither condition and stay excluded with **zero change to those specific assertions** (`test/external-only-agent.test.ts:14-52`).

### 4.4 Canonical role synthesis (replaces the draft's donor-fallback and plural-harness ideas)

**Structural fix to avoid a circular import:** `src/defaults.ts` currently imports from `src/profiles.ts` (`isExternalAgentProfile`, etc.), and the new synthesis logic must live in `src/profiles.ts` (where `resolveExternalProfile()` is), so `profiles.ts` cannot import `defaults.ts` without a cycle. Fix: extract the six-role definition table itself — currently the inline `DEFAULT_ROLES` const and `BACKEND_LABELS` map in `src/defaults.ts:13-47` — into a new dependency-free leaf module, `src/default-roles.ts`, exporting `DEFAULT_ROLES` and a small `roleDefinition(role): RoleDefinition | undefined` helper. `src/defaults.ts` imports from it for its existing per-CLI-backend seeding (`buildDefaultProfile()`, unchanged behavior); `src/profiles.ts` imports from it for pi-role synthesis. Neither of the two consumers imports the other.

**Resolution order in `resolveExternalProfile()`** (`src/profiles.ts:213-260`), for a `backend`-agnostic `role` + `harness` selection where `harness` names a registered pi config:

1. Look up `profiles.get(`${harness}-${role}`)` exactly as today. If a real on-disk file exists at that exact name (a user wrote `pi-deepseek-reviewer.md` or `pi-deepseek-security-reviewer.md` by hand, or via the profile creator — §7.4), it wins **for body/description/permission/tools** — this part of the lookup is the existing behavior, unmodified. Its `model`/`thinking` frontmatter fields are a different matter (see below): the on-disk file may customize *what the role does*, but not *which model/thinking `<harness>` names*.
2. On a miss, if `role` is one of the six keys in `DEFAULT_ROLES` (`explorer`/`planner`/`implementer`/`reviewer`/`qa`/`worker`) **and** `harness` is a registered pi config, synthesize an in-memory `SubagentProfile`: same `permission`/body shape as `roleDefinition(role)`, `backend: "pi"`, `harness: <name>`, `model`/`thinking` from the harness's registry entry, `name: `${harness}-${role}``, `description` templated with the harness label (the harness name itself, e.g. `"Repository exploration through pi-deepseek."` — there is no fixed product label for an arbitrary model the way there is for "Claude Code"/"Codex CLI"/"Antigravity"). Nothing is written to disk.
3. On a miss for any other role name, fail exactly as today (`Unknown external role...`).

This gives every registered `pi-*` config **immediate, automatic coverage of all six default roles**, sourced from the one place those six role bodies already live, with an explicit, simple override precedence for body content: **a real file always beats synthesis.** There is no ambiguity about which external CLI's customized body would apply, because none is ever consulted — the canonical source is fixed and singular.

**The harness registry, not the override file, remains authoritative for model/thinking.** A hand-authored `<harness>-<role>.md` naming `harness: <name>` inherits `<name>`'s registered `model`/`thinking` unless it omits those frontmatter fields entirely; if it *does* declare a `model` or `thinking` that differs from `<name>`'s current `harnesses.json` entry, that is a **configuration conflict, not a customization**, and `resolveExternalProfile` rejects it at resolution time with a diagnostic (`profile <name> declares harness <h> but pins model/thinking that conflicts with <h>'s registered config; remove the override or update harnesses.json`) rather than letting the on-disk file's values silently win. Two things motivate treating this as a hard reject instead of "the file wins, same as body/permission today": first, unconditional on-disk-wins for model/thinking would let a stale or hand-edited override file keep pointing at an old model after the harness's registered model was intentionally changed in `harnesses.json` — silently reintroducing the exact drift §8 fixes for the replay cache, but at the profile-resolution layer instead of the fingerprint layer. Second, and more directly: the whole point of the §4.3 legitimacy rule is that a `backend: "pi"` profile is only trustworthy to execute *because* its declared `harness` names something this extension's own registry validated (a resolvable model, configured auth) — a file that names a legitimate `harness` but then overrides that harness's model to something never validated would bypass that enrollment check while still appearing to pass it. Body/description/permission/tools carry no such trust implication, so they remain freely overridable; model/thinking do, so they are not.

This same override-precedence and snapshot-freezing logic must also survive workflow execution, where a synthesized profile is not looked up through `resolveExternalProfile` a second time — see §8 for the mechanism.

**Why automatic reuse, not opt-in, for execution-tier roles:** the existing default roster already auto-installs `implementer`/`qa`/`worker` (permission: `danger`) for every one of the three CLI backends unconditionally on first run (`seedDefaultProfiles`, `src/defaults.ts:86-103`) — there is no per-backend review gate today, and this design does not introduce a stricter standard for a fourth backend than the three that already exist.

This is **not**, however, because "danger" tier on a pi harness is materially safer than "danger" tier on an external CLI. It is not: the pinned SDK's `bash` built-in tool (§6) executes real host shell commands with the same effective reach as an external CLI's own shell access — full host access, not a sandboxed subset. The curated, builtins-only child surface established in §6 bounds *which tools exist at all* (no arbitrary project/user extension tools), which is a real, honest, and separately-justified restriction; it does not make the `bash` tool itself any less dangerous once it is present at `danger` tier. Treating pi's `danger` tier identically to the three CLI backends' `danger` tier is justified on its own terms — same unconditional precedent, same "the profile body is the only restraint once bash is granted" reality that already applies to agy/claude/codex — not on a false claim that the exposure is smaller.

## 5. Public selector surface & catalog

- `EXTERNAL_HARNESSES` / `ExternalHarness` stay **exactly as-is** in `src/types.ts:5-6` — "the three CLI-native harnesses." The private `isExternalHarness()` helper in `src/settings.ts:54-56` (not in `src/types.ts` as an earlier draft cited) widens to accept `pi-*` names alongside the three literals, since `resolveDefaultHarness` (`src/settings.ts:231`) uses it. A new runtime-only concept, "configured harness names" = `EXTERNAL_HARNESSES ∪ getConfiguredHarnessNames(agentDir)`, threads into `resolveExternalProfile`, `externalRoleAvailability`, and both tool parameter schemas.
- `agentToolParameters.harness` (`src/pi-subagent.ts:67-69`) and `externalHelpParameters.harness` (`src/external-help.ts:23-25`) both change from a hardcoded 3-literal `Union`/`StringEnum` to a plain validated `Type.String()` — mirroring how `role` is already a plain string, since the set is now dynamic (registry-backed) rather than closed. Error messages list the live set instead of `EXTERNAL_HARNESSES.join(", ")`, unchanged mechanism, wider content.
- `formatExternalRoleCatalog`/`roleLabel`/`buildCoordinatorPrompt` (`src/prompts.ts`) iterate the dynamic list instead of the literal `EXTERNAL_HARNESSES` array; the existing "(harness only)" partial-availability rendering already generalizes with no new UI concept, since it already works for any harness subset today.
- `permissionHelp()` (`src/external-help.ts:43-54`) re-keys by **backend** (4 entries: `agy`/`claude`/`codex`/`pi`) rather than by harness name, since permission semantics are backend-level, not per-config; it resolves a requested harness name to its backend first.
- `/external doctor` (`src/external-command.ts:79-99`): for harnesses resolving to `backend !== "pi"`, the existing `pi.exec(backend, ["--version"])` check is unchanged. For `backend === "pi"` entries, skip the CLI exec (there is no process) and instead confirm the registry's `model` resolves via `ctx.modelRegistry.find()` and report `ctx.modelRegistry.hasConfiguredAuth()` — both confirmed synchronous, no new async plumbing.
- `/external settings` (`settingsText()`, `src/external-command.ts:57-77`) gains a `Pi harnesses: pi-deepseek (deepseek/deepseek-chat · high), pi-glm (zhipu/glm-4.6 · default thinking)` line, or `Pi harnesses: none configured` — reusing the existing settings-text format, not a new subcommand.
- `defaultHarness` (global setting + trusted-project override, `src/settings.ts`) widens to accept configured `pi-*` names. Its **type** changes from `ExternalHarness` to `string` in `EffectiveDefaultHarness.harness` and in every `getDefaultHarness`/`getDefaultHarness(ctx)` callback signature (`pi-subagent.ts`, `workflow/tool.ts`, `external-help.ts`) — a real, mechanical, compiler-verified ripple (see §9). Validation is split in two: **shape** at settings-parse time (matches `pi-[a-z0-9][a-z0-9-]*` or one of the three literals — pure, no I/O, matching `parseSettings()`'s existing synchronous contract), and **live existence** lazily at resolution time (`resolveCtxDefaultHarness`/`resolveDefaultHarness`).

  These two resolution contexts must **not** be handled the same way, and this design corrects an earlier draft of this section that conflated them:
  - **Session-startup / advisory reads** — roster seeding, `/external settings`, `/external doctor` — may load and report a `defaultHarness` value even when the named `pi-*` config no longer exists in the live registry. These paths already tolerate a stale name today (a deleted `claude`/`codex`/`agy` profile doesn't crash them either), and surfacing "configured default `pi-deepseek` is not currently registered" as diagnostic text is itself useful, not a failure to avoid.
  - **An actual delegation that resolves to the default** (`Agent`/`workflow` called with no explicit `harness`, landing on a `defaultHarness` that names a deleted/invalid `pi-*` config) must **fail that call** with an actionable error — e.g. `default harness "pi-deepseek" is not registered (deleted from harnesses.json?); pass harness explicitly or recreate it via /external profile create` — **never** silently substitute `"agy"`. Silently rerouting a delegation the user explicitly pinned to one model onto an unrelated backend and model is a correctness and trust problem — a reviewer call meant for a specific pinned model would silently run on a different backend with different cost, behavior, and tool access — not a convenience worth preserving. This replaces the earlier "falls back to the hard-coded ultimate default (`agy`) with a diagnostic" behavior for the delegation path specifically.
  - The hard-coded `"agy"` ultimate default is unchanged, and still applies, for the genuinely different case of **no `defaultHarness` ever having been configured at all** (today's existing zero-default bootstrap) — that is not "was configured, then became invalid," and this design does not touch it.

## 6. Curated child extension/tool boundary (honest, not denylist theater)

**Problem with the status quo (dormant code):** `spawnSubagentRuntime`'s pi branch (`src/core/spawn.ts:494-505`) builds its `DefaultResourceLoader` with `extensionsOverride` that filters out only extensions whose tool set contains one of `CHILD_EXCLUDED_TOOLS` (`["Agent", "workflow"]`). Every other project- or user-installed pi extension — anything providing arbitrary custom tools — loads normally into the child. A "readonly" tier that excludes 4 built-in names by string match does nothing to that surface. This must not be described as an enforced boundary, because as coded it is not one.

**Resolution: curated, builtins-only child sessions.** `DefaultResourceLoader`'s documented options (`node_modules/@earendil-works/pi-coding-agent/dist/core/resource-loader.d.ts:61-113`) include exactly the primitive needed: `noExtensions`, `noSkills`, `noPromptTemplates`, `noThemes`. This repo's own test harness already constructs a `DefaultResourceLoader` this way today, safely, against this exact pinned SDK version (`test/helpers/pi-subagent-harness.ts:170-180`), so this is a proven-compatible combination, not a spike. The pi spawn branch changes to:

```ts
const resourceLoader = new DefaultResourceLoader({
  cwd,
  agentDir,
  settingsManager,
  noExtensions: true,
  noSkills: true,
  noPromptTemplates: true,
  noThemes: true,
  appendSystemPromptOverride: (base) => [...base, ...appendPrompts],
});
```

dropping the old `extensionsOverride` entirely (moot — no extensions load to filter). `noContextFiles` is left at its default (`false`), so project `AGENTS.md`/`CLAUDE.md`-style context text still loads — that is inert, already-trusted project text (already readable by the parent), not executable code, so excluding it would be an unjustified regression in a pi child's situational awareness relative to what an external-CLI child effectively gets from its own project-root startup.

With this change, a pi child's **entire tool surface is exactly**: the four SDK built-ins (`read`, `bash`, `edit`, `write` — confirmed exact lowercase names, `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.d.ts:96`, `.../dist/core/sdk.d.ts:40-42`) plus any explicit `customTools` this extension itself injects (e.g. `structured_output` for workflow schema capture). `CHILD_EXCLUDED_TOOLS` (`["Agent", "workflow"]`) is kept in the `excludeTools` list passed to `createAgentSession` purely as **defense-in-depth documentation of intent** — it is provably unreachable once `noExtensions: true` is set (this extension's own tools are never loaded into the child's resource set to begin with), and is retained anyway on the general principle of never relying on "this can't happen" for a security-relevant exclusion list. Nothing here claims "builtins only" prevents shell-based delegation in general — it only bounds what a pi *child* can load; `agy`/`claude`/`codex` children are unaffected and continue to have whatever tool/MCP surface their own harness and project configuration grant them, which this design does not touch.

**Provider-extension compatibility: verified for the data path, not yet exercised end-to-end.** A custom/self-hosted model provider registered dynamically by a pi extension (`ModelRegistry.registerProvider(providerName, config)`) is not lost by `noExtensions: true`, because the pi spawn branch already passes `modelRegistry: ctx.modelRegistry` — the **exact same, already-populated** registry instance from the parent — rather than constructing a fresh one.

What is actually confirmed, by direct read of the pinned package's compiled JS (`dist/core/model-registry.js:611-645`): `registerProvider` stores the provider's config (`applyProviderConfig`, `upsertRegisteredProvider`) **inside the `ModelRegistry` instance itself** — the same object reused for a live model's request/auth resolution (`getApiKeyAndHeaders`, `hasConfiguredAuth`). Since the child spawn reuses that exact instance rather than a fresh `ModelRegistry.create(...)`, a dynamically-registered provider's model listing and auth resolution are mechanically available to a pi child with no extension reload, confirmed from source rather than assumed.

What is **not yet verified**, and should not be claimed as settled: whether every real-world provider extension in the wild depends on anything *beyond* registry data — e.g. a custom tool, a request-shaping hook, or other extension-provided behavior tied to that provider — since `noExtensions: true` does drop all of that regardless of the registry-sharing above. This design's claim is scoped precisely to "the registry data a provider registration writes survives"; broader "any provider extension will just work" compatibility is untested and should be validated against a real third-party provider extension during field testing (`docs/field-testing.md`), not assumed from this source read alone.

**Tier → tool-exclusion table** (confirmed against the pinned SDK's actual built-in tool set — `dist/core/sdk.js:131`, `defaultActiveToolNames = ["read", "bash", "edit", "write"]` — no `powershell` tool exists in this package):

The pinned SDK exposes **seven** built-in tool factories, not four: `read`, `bash`, `edit`, `write` (the four activated by default when no explicit `tools:` allow-list is given) plus `grep`, `find`, `ls` (`createGrepTool`/`createFindTool`/`createLsTool`, `dist/core/tools/index.js`) — read-only search tools that exist and are constructible by name, but are **not** in `defaultActiveToolNames` and so are absent from a pi child unless a profile's own `tools:` allow-list names them explicitly. This matters concretely: `explorer` and `reviewer` are both seeded at `readonly` (`src/defaults.ts`'s `DEFAULT_ROLES`), and a synthesized pi profile for either role carries no `tools:` allow-list — under a `readonly` exclusion of `bash`/`edit`/`write` alone, such a child's *only* usable tool would be `read` against paths it already knows, with no way to search the repository at all. That is not a meaningful "read-only exploration" capability. The tier table below therefore explicitly allow-lists the read-only search tools at `readonly`/`edit` tiers (via `tools:`, not just narrowing `excludeTools`), so a `readonly` pi child gets `read`/`grep`/`find`/`ls` — genuinely useful and still incapable of mutation — rather than a token gesture at "read-only" that is unusable in practice:

| Tier | Active tools (`tools:` allow-list, when the profile itself sets none) | Excluded (`excludeTools`, in addition to `CHILD_EXCLUDED_TOOLS`) |
| --- | --- | --- |
| `readonly` | `read`, `grep`, `find`, `ls` | `bash`, `edit`, `write` |
| `edit` | `read`, `grep`, `find`, `ls`, `edit`, `write` | `bash` |
| `danger` | (SDK default: `read`, `bash`, `edit`, `write`) | (none beyond `CHILD_EXCLUDED_TOOLS`) |

A profile that sets its own explicit `tools:` allow-list is unchanged by this table (the profile's list is intersected with the tier's `excludeTools` exactly as `createAgentSession`'s documented "excludeTools applies after tools" contract already guarantees, `.../dist/core/sdk.d.ts:45-46`) — the table above only supplies a *default* allow-list for `readonly`/`edit` tier when the profile itself is silent, so those two tiers are actually usable out of the box.

**No `toolsUnconstrained` warning.** An earlier pass of this design proposed warning (`policy_warning`, `toolsUnconstrained: true`) when a profile at `edit`/`danger` tier carries no `tools:` allow-list, reasoning that the curated builtins-only ceiling made "unconstrained" a low-severity condition worth flagging but not blocking. That reasoning rested on the same false premise corrected above: curation bounds which tool *names* can exist, not what `bash` can do once it is one of them. A `danger`-tier pi child with no `tools:` allow-list already gets exactly the SDK's four default tools (`read`/`bash`/`edit`/`write`) — the same as every other `danger`-tier profile on any backend, curated or not — so there is nothing distinctively "unconstrained" about it to disclose, and this design drops the warning entirely rather than keep a disclosure built on an inaccurate premise. Permission tiers here remain what they have always been for this extension: a truthful **tool-level** restriction (which named tools are wired into the child), never an OS-level sandbox boundary — that framing is unchanged and applies identically to pi.

## 7. SDK runtime execution contract — all questions resolved against the pinned package

All facts below are read directly from `node_modules/@earendil-works/pi-coding-agent` at the **pinned devDependency version, `0.79.4`** (`package.json:3`), not the newer globally-installed `pi` CLI (`0.85.1`) that was used for background docs reading in the earlier draft. Nothing in this section depends on the newer CLI; where the two might differ, the pinned package's compiled `.d.ts`/`.js` is the ground truth cited.

### 7.1 Model resolution and auth preflight

`resolveProfileModel()` (`src/core/model.ts:19-24`) removes its `: ctx.model` fallback for `backend: "pi"` profiles. This is safe to scope exactly to profiles that reach this function, because only *legitimate* pi profiles (real file or synthesized, per §4.3–4.4) ever reach it — `resolveExternalProfile()` already filters out any illegitimate `backend: "pi"` profile earlier in the same call. A pi profile with no resolvable `model` becomes a hard, immediately surfaced error: "profile `<name>` pins no resolvable model" (unparseable `provider/id` string) vs. "model `<x>` not found in registry" (parseable but absent) — two distinct messages from a discriminated result, not one vague one.

Before constructing the child session: `ctx.modelRegistry.hasConfiguredAuth(model)` (confirmed synchronous, "fast check that doesn't refresh OAuth tokens" — `.../model-registry.d.ts:52-56`) gates entry with a clean "no credentials configured for provider `<x>`" error, rather than a confusing mid-run provider error two SDK layers down. The check's own doc comment is the honest caveat to carry into user-facing text: it does not proactively refresh OAuth, so a token that only needs silent refresh could show as unconfigured — acceptable, since the underlying prompt() call would then simply also fail cleanly with a provider error, not silently misbehave.

### 7.2 Thinking level — SDK clamping is real but does not cover typo/garbage input; an explicit preflight is required

Two confirmed facts:

1. `createAgentSession({ thinkingLevel })`'s own documented contract clamps to model capability: *"Thinking level. Default: from settings, else 'medium' (clamped to model capabilities)"* (`.../dist/core/sdk.d.ts:22-23`), backed by `AgentSession`'s private `_clampThinkingLevel` and public `getAvailableThinkingLevels()`/`supportsThinking()` (`.../dist/core/agent-session.d.ts:426-440`).
2. `Model<Api>` (`node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/pi-ai/dist/types.d.ts:488-511`) exposes `reasoning: boolean` and an optional `thinkingLevelMap?: Partial<Record<"off"|"minimal"|"low"|"medium"|"high"|"xhigh", string | number | null>>` — a level absent from the map uses provider defaults; `null` explicitly marks it unsupported.

Both facts describe **capability clamping**: a *valid* level (one of the six literals in §4.2) that a *specific model* doesn't support is gracefully downgraded. Neither fact says anything about an *invalid* level — a typo, an outdated value from before this repo's own SDK bump, or a hand-edited `harnesses.json` entry that predates §4.2's validation. `thinkingLevel` is typed as the closed `ThinkingLevel` union only at the TypeScript boundary inside the SDK's own source; nothing enforces that at the JSON-on-disk boundary this design introduces. Silently letting the SDK "clamp" a typo'd string is not the same as clamping an out-of-range but real level, and the earlier pass of this design conflated the two by citing fact (1) as if it covered both cases.

**Fix:** keep §4.2's load-time/creation-time validation (an unsupported `thinking` string is dropped from the registry, or rejected before write, with a diagnostic — never silently passed through). Additionally, immediately before constructing the child session, re-validate the resolved `thinking` value against the same closed six-literal set and fail with a clear `unsupported thinking level "<value>"; expected one of off/minimal/low/medium/high/xhigh` error if it somehow reached this point outside the set (defense-in-depth against a registry file edited or restored out-of-band since it was last loaded). Only a value that passes this check reaches `createAgentSession`, whose model-capability clamp (fact 1) then legitimately downgrades it if the resolved model specifically can't support it — that clamp, and only that clamp, is what the existing disclosure step below is for.

**Clamp disclosure (kept from the earlier draft, scope narrowed):** after `createAgentSession(...)` resolves, compare the session's actual `session.thinkingLevel` getter (`.../dist/core/agent-session.d.ts:264`) to the (now-validated) requested `thinking`. If they differ, record a `thinkingClamped: { requested, effective }` evidence field and surface it in the receipt banner the same way permission elevation already is (`src/core/spawn.ts:184-186`). This disclosure now exists purely to reveal legitimate *model-capability* clamping — never to paper over a value that should have failed outright at the preflight step above.

### 7.3 Auth preflight and smoke test reuse

Both `ModelRegistry.find()` and `ModelRegistry.hasConfiguredAuth()` are confirmed synchronous (§7.1), safe as an in-tool-call preflight with no added latency concern. The profile-creator's existing real-backend smoke test (`installProfileWithSmokeTest`, `src/profile-creator.ts:104-177`) is reused verbatim for pi-harness creation (§4.2, §8) — creating a `pi-*` harness entry now genuinely exercises this same completed runtime end to end, the same assurance claude/codex/agy profile creation already gets from spawning the real CLI.

### 7.4 Terminal completion — kept, one fallback removed, "non-empty" tightened to "non-whitespace," and the terminal event is observed rather than inferred

The existing dormant definition of "done" is close to correct and is **kept with two tightenings**: `session.prompt()` resolves without throwing, `getFinalAssistantFailure(session.messages)` returns `undefined`, and `extractFinalAssistantText(session.messages)` is non-empty (`src/core/spawn.ts:556-591`).

1. **Non-empty → non-whitespace.** The current `|| "(no final text output)"` fallback (today treated as **success**, `src/core/spawn.ts:573`) is removed — but the replacement check must not just be "string length > 0." A final assistant turn consisting only of whitespace (e.g. a stray newline) is exactly as hollow as a genuinely empty string and must fail the same way; the check is `extractFinalAssistantText(session.messages)?.trim()` being non-empty, not the raw string. An empty-or-whitespace-only final answer becomes an explicit thrown error, routed through the existing `catch` block's `status: signal?.aborted ? "aborted" : "error"` logic — no new status value, only a new failure cause. This is the in-process translation of `CONTEXT.md`'s "zero-exit + recognized terminal event + non-empty result" definition (`CONTEXT.md:16`), and matches this repo's own already-approved (but not-yet-implemented) supervision design's principle 4, *"Output survives failure without becoming a successful result"* (`feat/child-supervision-foundation` branch, `docs/plans/2026-09-14-child-observation-and-supervision-design.md`) — this change is consistent with that direction, not in tension with it.

2. **The nonretry terminal event is observed, not merely argued to be implied.** `AgentSessionEvent`'s `agent_end` variant carries `willRetry: boolean` (`.../dist/core/agent-session.d.ts:40-46`). The reasoning that a terminal `agent_end` observed after `await session.prompt()` resolves can never have `willRetry: true` (because the SDK's own auto-retry, §7.6, already ran to completion internally by then) is sound, but this design does not rely on that reasoning alone as the safety mechanism: the `session.subscribe` callback (already wired for `onBackendEvent`, §7.5) captures the **last** `agent_end` event seen before `prompt()` resolves, and success is only declared once that captured event's `willRetry` is confirmed `false` — an explicit assertion, not an inferred one. If a future SDK version's internal retry timing ever changed such that a genuinely-retrying `agent_end` could reach this point, this check fails loudly (treated as an unexpected-state error) instead of silently reporting success on a turn the SDK itself considered non-final.

3. **No completion while tools are still running.** `await session.prompt()` already only resolves once the full turn (including any in-flight tool calls) has settled — this is an existing property of the SDK's `prompt()` contract, not new behavior — but this design states it explicitly as an invariant the pi branch depends on: the terminal-completion check (points 1–2 above) must only run after that await returns, never from an intermediate `message_end`/tool-call event observed inside the `subscribe` callback. The existing code already satisfies this (the completion check is after `await session.prompt(...)`, not inside the event callback); this is recorded here so a future refactor cannot accidentally move the completion decision earlier.

4. **Cleanup ownership around session setup/subscription failures.** The existing `finally` block (`unsubscribe?.()`, abort-listener removal, `session.dispose()`, `src/core/spawn.ts:612-619`) only runs once execution reaches the `try` that wraps `bindExtensions`/`prompt`. If `createAgentSession(...)` itself throws (model/auth preflight failure, §7.1), no session exists yet and there is nothing to dispose — already correctly a non-issue. But `resourceLoader.reload()` (§7.7's new third abort guard sits immediately after this call) and `session.subscribe(...)` both run **before** the `try` block; if either throws, the function exits without reaching `finally`, potentially leaking the subscription or an already-constructed session. This design requires moving session construction, `resourceLoader.reload()`, and `session.subscribe(...)` inside (or ahead of, with their own narrow `try`/cleanup) the same ownership boundary as the main `try`/`finally`, so that a failure during setup — not just during the prompt turn — still disposes anything that was actually constructed. This is a correctness gap in the dormant code, not a hypothetical: `resourceLoader.reload()` does real file I/O and can throw on a malformed project config.

### 7.5 Evidence: wiring `onBackendEvent`

`params.onBackendEvent` is currently never called in the pi branch (`backendEventCount`/`nestedActivitySeen` always `0`/`false` for pi runs today). Fix: call it from inside the existing `session.subscribe((event) => {...})` callback (`src/core/spawn.ts:532-544`) for every event, mirroring how the other three backends already feed their own event streams into it. `hasNestedAgentActivity()` (`src/core/spawn.ts:105-129`) correctly gets **no new `"pi"` case** — a pi child structurally cannot spawn further nested agents (`Agent`/`workflow` are excluded from its tool set, and after §6 no extension could reintroduce them), so `nestedActivitySeen` staying `false` for pi is *correct*, not a gap; only `backendEventCount` needed the wiring fix.

### 7.6 Retry — the SDK auto-retries by default; this design must disable it per child, in-memory only, without touching the user's real settings

Confirmed directly in the pinned package's compiled JS (`.../dist/core/settings-manager.js:535-551`, `.../dist/core/agent-session.js:1958-2040`): `AgentSession` has its **own built-in auto-retry** for transient provider errors, independent of anything this extension does. Defaults: `enabled: true`, `maxRetries: 3`, `baseDelayMs: 2000` with exponential backoff (`delayMs = baseDelayMs * 2^(attempt-1)`, i.e. up to ~2s/4s/8s of internal waiting), read from whatever `SettingsManager` instance is passed to `createAgentSession`. It retries on rate-limit/5xx/network/timeout-shaped errors (regex-matched, `_isRetryableError`) and explicitly excludes context-overflow (handled by compaction) and quota/billing-exhaustion errors (`_isNonRetryableProviderLimitError`). All of this happens **inside** `session.prompt()`, before it resolves — by the time this extension's own `getFinalAssistantFailure` check runs, any internal retries are already exhausted or successful.

**This conflicts with this repo's own no-auto-retry contract** (`AGENTS.md`, "Receipt and evidence invariants": *"Do not automatically retry failed or aborted external runs... Exception: the agy backend retries once on infrastructure-classified failures... never applies to agent-level failures, aborts, or timeouts"*). An earlier pass of this design passed the **real, on-disk** `SettingsManager.create(cwd, agentDir)` into the pi branch unmodified and treated the SDK's default auto-retry as simply "existing, already-active host behavior" this extension has no business overriding. That is not correct: if left as-is, every pi child would silently retry up to 3 times on a transient failure with zero disclosure and zero way for this extension's own no-auto-retry contract to hold for a fourth backend — a real gap this design must close, not an acceptable inherited default.

**Fix:** the pi branch must construct the child session with retry **disabled**, scoped to that child only, and must never write this override to the user's real global or project Pi settings file. Two mechanically equivalent ways to do this (implementer's choice, constrained to "no persistence, no shared-file mutation"):
- Build the child's effective settings from an **in-memory snapshot/override** of the real `SettingsManager` (mirroring the already-established `SessionManager.inMemory(cwd)` idiom this branch already uses for the child's session store, `src/core/spawn.ts:515`) that reports `retry.enabled: false` regardless of what the user's on-disk settings say, while every other real setting (auth, models, defaults) still flows through unchanged; or
- If the pinned SDK's `SettingsManager`/`createAgentSession` surface exposes a narrower per-call retry override (implementation-time check against the pinned package — confirm whether one exists before assuming it doesn't), use that instead of building a wrapper.

Either mechanism must be **transient and call-scoped**: never written to the user's real settings file, never persisted across pi children, and never described as something that "cannot be disabled here." The correct framing for user-facing disclosure (`external_help` topic `permissions`, and the pi entry in `permissionHelp()`'s backend map) is: *"pi children disable the SDK's own ambient auto-retry by default (in-memory, per-child) to honor this extension's no-auto-retry contract; a pi call therefore fails immediately on a transient provider error rather than silently retrying, unlike ordinary interactive Pi sessions."* If a future need arises for a pi child to opt into retry (mirroring agy's narrow, disclosed, infra-classified-only exception), that would be a new, explicitly disclosed exception requiring its own design sign-off — not the default this design ships.

### 7.7 Cancellation and cleanup

Two existing pre-abort guards are kept (before `bindExtensions`, before `session.prompt`); one guard is **added**, immediately after `resourceLoader.reload()` (currently unguarded and potentially slow if many project resources are configured — even with `noExtensions: true`, `reload()` still does file I/O for context files and settings). `session.abort()` is confirmed **cooperative only** (per the SDK's own extensions docs describing `ctx.signal`/`ctx.abort()`) — no guarantee of hard-killing an in-flight tool call, unlike SIGTERM on an external CLI's whole process tree. This asymmetry is disclosed in user-facing permission/cancellation text, not silently assumed away.

Cleanup (`unsubscribe?.()`, abort-listener removal, `session.dispose()`) is complete for the case the existing `finally` block already covers (`src/core/spawn.ts:612-619`) — **but, per §7.4 point 4, that block only runs once execution reaches the `try` wrapping `bindExtensions`/`prompt`.** `resourceLoader.reload()` and `session.subscribe(...)` both run before that `try`; this design extends cleanup ownership to cover a throw from either of those two calls as well (whichever of the resource loader, session, or subscription actually got constructed before the throw), not just a throw during the prompt turn itself. This is a real gap in the dormant code, since `reload()` does file I/O that can fail.

### 7.8 Resume — deliberately not supported, already correct

No code change needed, confirmed by direct trace: the pi branch never sets `details.sessionId` because the child uses `SessionManager.inMemory(cwd)` (`src/core/spawn.ts:515`) and is `dispose()`d at the end — there is no persisted session to resume even in principle. `resolveResume()` (`src/core/resume.ts:16-43`) already produces a clean, specific error — *"Run record `<id>` has no session id to resume"* — for any pi run, with zero special-casing. This is stated here as a **deliberate v1 non-goal**, not an oversight: making pi children resumable would require persisting the in-memory session, which is a materially larger change (session-file lifecycle, storage, and the concerns the not-yet-implemented supervision design is already working through on `feat/child-supervision-foundation`) that this design does not take on.

### 7.9 Budget — already generalizes correctly, zero code change

`spawnSubagent`'s existing budget-evidence logic (`src/core/spawn.ts:319-324`) already writes `budgetEnforceable: false` for any backend other than `"claude"` — this condition already covers `"pi"` with no change. No mid-run cost-check loop is added for pi, for the same reason the earlier draft gave and this design keeps: `session.getSessionStats()` cost data is only available after a turn completes, and layering a hard stop on top of already-cooperative-only cancellation (§7.7) would compound two soft guarantees into something that is not a real cap. Explicitly deferred, not silently missing.

## 8. Cross-cutting: replay-cache fingerprint and profile-snapshot freezing — resolved execution identity

**Problem, traced precisely:** `fingerprintWorkflowAgentCall()` (`src/workflow/replay-cache.ts:4-16`) hashes `call.subagentType` — the **resolved profile name string** (e.g. `"pi-deepseek-reviewer"`) — never the profile's `model`/`thinking`/`backend`/`systemPrompt`/`tools`/declared `permission`/declared `maxBudgetUsd`. Editing `harnesses.json` to point `pi-deepseek` at a different model, or editing a markdown profile's `systemPrompt`/`tools`/`permission`/`maxBudgetUsd` frontmatter, does not change the string `"pi-deepseek-reviewer"`, so a stale replay-cache entry from before the edit incorrectly appears to match after it. This is a pre-existing latent gap for **all** backends, not pi-specific, that becomes materially more likely to bite with frequently-retuned named pi configs.

**A second, sharper problem the earlier pass of this section missed:** the fix cannot be "have `runtime.ts` ask for a descriptor and fall back gracefully if none is available," because the actual execution path has the identical blind spot the fingerprint does. `workflow/tool.ts`'s `execute()` builds `profiles` **once**, at the top of the run (`const profiles = filterExternalAgentProfiles(filterProfilesForModelRegistry(getSubagentProfiles(getAgentDir()), ctx.modelRegistry));`, `workflow/tool.ts:118`) — this map is populated **only from on-disk profile files**; it never contains a canonically-synthesized pi role (§4.4's synthesis happens inside `resolveExternalProfile()`, which nothing in `workflow/tool.ts` calls). Every later consumer of this map — `runAgent`'s actual execution lookup (`profiles.get(call.subagentType)`, `workflow/tool.ts:139`, whose failure path is "Unknown external subagent_type"), and the `onAgentQueued`/`onAgentStart` UI callbacks (`profiles.get(event.subagentType)?.backend`, `workflow/tool.ts:309,327`) — reads from this same un-synthesized map. Concretely: **a workflow cannot invoke `role: "reviewer", harness: "pi-deepseek"` today under this design unless `pi-deepseek-reviewer.md` happens to exist on disk**, even though the `Agent` tool's own `resolveExternalProfile()` path would happily synthesize it. This is a real functional gap, not just a fingerprinting nuance, and it means the fingerprint-descriptor fix must not be layered on top of it as an "optional, best-effort" addition — a `describeSubagentType?: (name) => ... | undefined` that silently returns `undefined` for every synthesized pi profile would make the fingerprint fix pointless for exactly the case that motivated it, while leaving the underlying execution gap (workflows can't run synthesized pi roles at all) unfixed.

**Fix: freeze one resolved roster snapshot per workflow run, synthesized profiles included, and make every consumer — execution, callbacks, and the fingerprint descriptor — read from that same snapshot.**

1. At the same point `profiles` is built today (`workflow/tool.ts:118`), after loading the harness registry (`loadHarnessConfigs(agentDir)`), additionally synthesize the six canonical role profiles (§4.4) for every registered `pi-*` harness **and insert them into the same `profiles` map**, skipping any `${harness}-${role}` key that already has a real on-disk entry (identical override precedence to §4.4, applied once, up front, for the whole run — not re-decided per call). This map — real on-disk profiles plus synthesized pi-role profiles, merged once — **is** the frozen roster snapshot for the run; nothing later in the workflow re-resolves a profile through `resolveExternalProfile()` or re-reads `harnesses.json`, so a `harnesses.json` edit mid-run cannot produce a workflow where the fingerprint disagrees with what actually executed (no TOCTOU gap between descriptor and execution).
2. With synthesized profiles now present in `profiles`, `runAgent`'s existing `profiles.get(call.subagentType)` (`workflow/tool.ts:139`) finds them with **zero change to that line** — the gap closes as a side effect of freezing the snapshot correctly, not through a new lookup path. The same is true for the `onAgentQueued`/`onAgentStart` backend-label callbacks.
3. `CreateWorkflowToolOptions`/`runWorkflow`'s options gain `describeSubagentType: (name: string) => Pick<SubagentProfile, "backend" | "harness" | "model" | "thinking" | "systemPrompt" | "tools" | "permission" | "maxBudgetUsd"> | undefined`, implemented in `workflow/tool.ts` as `(name) => profiles.get(name)` against the **same, now-complete** snapshot from step 1. Because the snapshot is complete, this callback is **not optional for correctness** in the sense of "may reasonably return `undefined` for a legitimate call" — a `undefined` result now only ever means the name genuinely doesn't resolve (the same failure `runAgent` itself would hit), never "it was synthesized and nobody told the descriptor." `runtime.ts` calls it once, right where `subagentType` is resolved (`src/workflow/runtime.ts:159-189`), and passes the result into `fingerprintWorkflowAgentCall`.
4. `runtime.ts` also computes the **actual effective permission tier** for the call — `resolveEffectivePermissionTier(call.permission, descriptor, options.getDefaultPermission())`, reusing the existing shared resolver from `src/core/permissions.ts` verbatim, not a duplicated tier-resolution rule — and includes that computed tier in the hashed object as `effectivePermission`, alongside the raw requested `call.permission`. This resolves the earlier draft's "known residual scope" note by using the real resolver instead of accepting the gap: an agy call's coercion to `danger` regardless of what was requested is now reflected in what gets hashed, at zero duplicated logic, since the resolver is imported, not reimplemented.
5. The hash also includes a coarse **resource/tool policy identifier** — e.g. the pinned `@earendil-works/pi-coding-agent` package version already read for §7's facts, plus a small literal tag for this extension's own tier→tool-exclusion table (§6) — so that a future change to *this extension's* curated tool policy (which tools a tier grants) also invalidates stale cache entries, the same way a model/thinking change does. This is deliberately coarse (a version/tag pair, not a full tool-list hash) since the goal is cache invalidation on policy change, not a security boundary.

**What the fingerprint hashes after this fix**, uniformly for **all** backends (not pi-only, since the gap is general): `call.prompt`, `call.context` (already present, kept — see the correction below on what this actually represents), `label`, `phase`, `subagentType` (name), `schema`, `call.permission` (the requested tier, kept for continuity with existing cached entries' shape), `maxBudgetUsd`, `resumeRunId` (already present), **plus, new:** `descriptor.backend`, `descriptor.harness`, `descriptor.model`, `descriptor.thinking`, `descriptor.systemPrompt`, `descriptor.tools`, `descriptor.permission` (the profile's own *declared default* tier, distinct from the call-site request), `descriptor.maxBudgetUsd` (the profile's own declared default budget, distinct from the call-site request), `effectivePermission` (step 4), and the resource/policy identifier (step 5).

**Correction to how `call.context` should be described:** the earlier pass of this section called `call.context` "the existing 'context provenance' evidence... already captured per-call and already part of the hash," implying it is what authenticates the actual shared text. That overstates what `ParentContextReceipt` is: per `src/core/parent-context.ts:12-19`, it is exactly `{ mode, requestedTurns?, sharedTurns, messages, bytes, compacted }` — **shape/receipt metadata about how context was shared** (which mode, how many turns, a message count, a byte count, whether history was compacted), not a hash or copy of the shared text itself. The actual shared text is not missing from the hash, though: `runtime.ts`'s `runAgentCall` builds `call.prompt` from `prepareParentContext(...)`'s returned `taskPrompt` (`src/workflow/runtime.ts:155-157`), which **already embeds the full JSON transcript of shared messages inline in the prompt string itself** (`src/core/parent-context.ts:100-108`). So content hashing of the actual shared text is preserved — it happens via `call.prompt`, which was already being hashed before this fix and remains so — while `call.context` contributes only the receipt-shape metadata alongside it. Fixing the description matters because a future reader should not conclude that removing or narrowing `call.context` would remove content provenance from the hash; it would only remove the shape/receipt metadata, since the content itself lives in `call.prompt`.

Small, isolated, backward-compatible for callers that don't yet wire `describeSubagentType` (e.g. a test harness): existing cached fingerprints simply miss once (recompute) after this change ships, since the hash inputs changed shape; a caller with no descriptor available falls back to hashing without the new fields, exactly as today, for that non-execution-path case only.

## 10. Profile-creation flow (`/external profile create`) — three branches, backward compatible

The interview forks into three, not two:

1. **Declare a new named Pi harness config** (no role): prompts for a `pi-<suffix>` name, a `provider/model` id validated live against `ctx.modelRegistry.find()` (reject immediately with the live model list on mismatch), optional thinking level. Runs through `installHarnessConfigWithSmokeTest` (§4.2, §7.3) — a real smoke-tested write to `harnesses.json`, staged/atomic/rollback-on-failure exactly like a markdown profile.
2. **Role profile for an existing external CLI harness** (`claude`/`codex`/`agy`) — today's flow, unchanged, except `profileParameters.backend` is internally renamed in spirit to "harness" (parameter name and validation widen; behavior for these three is identical).
3. **Role profile for an existing registered `pi-*` harness** — a new branch for the case where a user wants a role *not* in the shared six (e.g. `pi-deepseek-security-reviewer`). Goes through the same `compileProfile()`/`installProfileWithSmokeTest()` path already used for external CLI profiles, with `backend: pi` + `harness: <name>` frontmatter, and the *real* smoke test now exercises the completed pi runtime (§7.3) instead of always failing on the old hard-reject.

`PROFILE_INTERVIEW_PROMPT` is rewritten to ask which of the three the user wants, up front, before collecting further detail. `compileProfile()`'s naming rule changes from `profile.name.startsWith(`${backend}-`)` to `profile.name.startsWith(`${harness ?? backend}-`)`.

**Decided, not a review point:** the `if (profile.backend === "pi")` block in `pi-subagent.ts` (§9) must be removed or replaced with a check equivalent to the widened legitimacy predicate itself (i.e. re-derive "is this the same rejection `filterExternalAgentProfiles` would already apply" rather than an unconditional `backend === "pi"` test). Once §4.3 admits legitimate pi profiles through the catalog, the old block is not inert dead code sitting downstream of an already-filtered list — it is a second, independent, *unconditional* gate on the exact same field the legitimacy rule now needs to let through selectively. Leaving it unconditional would silently break the feature for every legitimate call; keeping "an inert guard, just in case" was never actually on the table once admission became conditional rather than absolute. No TOCTOU gap exists either way (both calls use the same `profiles` map instance within one synchronous tool execution), so the only real choice is *how* to express the replacement check, not *whether* to change it.

**Approved v1 scope:** Pi children use built-in tools only and load no child extensions, skills, prompt templates, themes, or MCP tools. The six canonical roles are shared automatically; custom roles remain per named Pi harness in v1. Pi resume and a hard budget cap are intentionally unsupported and disclosed. Expansion is tracked in [GitHub issue #43](https://github.com/tranhoangnguyen03/pi-flow-external/issues/43), including trusted capability opt-ins, shared custom roles, resumable sessions, and honest cost controls.

## 11. Compatibility summary — nothing about `agy`/`claude`/`codex` changes

Every existing `agy-*.md`/`claude-*.md`/`codex-*.md` file, every existing test asserting their behavior, every existing CLI-facing permission/argv-building function (`buildPermissionArgs`, `resolveEffectivePermissionTier`'s agy/claude branches) is untouched by this design. The only shared surface that widens is: the `harness`/`role` selector types (literal union → dynamic string set), `resolveExternalProfile`'s harness-name-set parameter, and the settings `defaultHarness` type — all backward compatible (an omitted or `agy`/`claude`/`codex`-valued `harness` behaves identically to today).
