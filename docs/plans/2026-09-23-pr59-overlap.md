# PR #59 / #65 overlap assessment

PR #59 merged into main as `19d3d2d9291bb62fa3b98d4abe21164f26e901ec`, introducing 2.5.0-external.0. PR #65 was implemented against the preceding tree. Product-owner direction: keep #65 on v2, targeting 2.6.0-external.0 with release:minor, while retaining explicit breaking-update disclosure.

## Semantic overlap and required reconciliation

1. **Shared roles are overlapping implementations.** #59's `subagents/pi-<role>.md` with literal `harness: pi-*` shares roles across Pi harnesses only. #65's extension-owned `roles/<role>.md` shares across all harnesses and stops reading subagents. Conversion must recognize wildcard templates explicitly rather than exclude them as native Pi profiles. Preserve their Pi-only scope and capability selection; do not automatically broaden privileged Pi-specific instructions across CLIs. Decide a single supported representation (e.g. an explicit Pi-only scope in shared roles); do not retain parallel runtime template resolvers.
2. **Capabilities must survive the redesign.** #59 adds `capabilitySet` and malformed-selection error propagation, named global/project `piCapabilitySets`, selected-resource loading, trust gates, content hashes, prelaunch drift validation, receipt disclosure and replay fingerprinting. #65 must preserve all of these in its canonical catalog, authoring/serialization, configuration save/conversion, inspection, direct invocation, and frozen workflow path.
3. **Current #65 upgrade would not preserve #59 templates.** A wildcard template's filename does not start with the literal `pi-*-` harness prefix. Its Pi profile can be classified as native/excluded, silently losing availability after v4 activation. Add a conversion fixture owning this behavior.
4. **Shared role validation conflicts with capability opt-in.** #65 permits only description/permission in shared role frontmatter. Simply copying #59 templates into roles would be invalid, and the complete-profile serializer needs to retain capabilitySet. Model capability eligibility explicitly rather than silently dropping the selection on CLI binding.
5. **Project settings contract has expanded.** #65's defaultHarness-only project schema/documentation predates #59's trusted project capability-set overrides. Preserve the newly shipped trust-gated whole-entry replacement behavior and never mistake untrusted settings for an allowed overlay.
6. **Catalog/command discovery must remain one surface.** Move #59's capability diagnostics and disclosures into new roles/inspect/settings/doctor commands; do not resurrect the removed profiles command. Remove stale instructions claiming Pi children can never load skills/templates; retain no extensions/MCP/themes.
7. **Workflow failure receipts must survive.** Keep #59's fix finalizing queued records for pre-spawn failures, plus capability propagation through agent-snapshot and workflow results.

## Integration sequence

- Merge current main into #65 without selecting one side wholesale.
- Resolve the single shared-role scope/capability representation first, then adapt #59's existing capability implementation to the canonical resolver.
- Extend conversion, creator serialization, project-trust and replay tests; migrate #59's fixtures to v4/roles/overrides.
- Reconcile all human/agent documentation and keep the 2.5.0 changelog entry alongside the proposed 2.6.0 entry.
- Rerun typecheck/offline suite, pack/audit, and named-Pi direct/workflow capability/drift smoke. Prior #65 results remain historical until this is complete.

This assessment does not claim the conflicts are resolved. Keep #65 draft and do not merge either side away. No live user configuration was changed during this check.
